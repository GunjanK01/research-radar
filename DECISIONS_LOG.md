### D001 — Data source: OpenAlex over arXiv
**Date:** 2026-08-15
**Decision:** Use OpenAlex API for paper ingestion.
**Why:** Free, no key, richer structured metadata (authors with IDs, topics/concepts,
citation counts) than arXiv, which reduces schema-design guesswork.
**Alternative considered:** arXiv API — simpler but thinner metadata, would need more
normalization work for authors/topics.

---

### D002 — Part 3 AI feature: Find similar papers
**Date:** 2026-08-15
**Decision:** Build "find similar papers" over "summarize and simplify" or "reviewer suggestion."
**Why:** JD frames the role as systems/platform engineering, not GenAI research, and explicitly
lists "vector search" and "embedding API integration into product surfaces" as good-to-haves.
Similarity search is a genuine systems problem (embedding generation, vector storage, indexed
query) rather than a thin LLM API wrapper. Also removes any external API dependency, making
the Docker demo more reliable for the evaluator.
**Alternatives considered:**
- Summarize and simplify — simplest, but demonstrates prompting more than platform skill;
  every applicant likely picks this.
- Reviewer suggestion — risk of arbitrary-feeling output given only 300–500 papers may not
  have enough author overlap across 2 topics to be defensible.

### D003 — Embedding approach: sentence-transformers (local) over OpenAI/Anthropic embeddings API
**Date:** 2026-08-15
**Decision:** Use `all-MiniLM-L6-v2` via sentence-transformers, run locally in the container.
**Why:** No API key needed anywhere in the stack; evaluator's `docker compose up` isn't
dependent on external service availability or the candidate's API credits.
**Alternative considered:** TF-IDF (scikit-learn) — lighter image, zero ML dependency, but
weaker semantic matching. Kept as fallback if the sentence-transformers image proves too heavy
for a comfortable 10-minute build.

---

### D004 — Keyword search: Postgres full-text search over Elasticsearch
**Date:** 2026-08-15
**Decision:** Use Postgres `tsvector`/`ts_rank` for title/abstract keyword search.
**Why:** Assignment explicitly rewards scope control ("do not gold plate"). Elasticsearch adds
a 4th service and operational complexity with no proportional benefit at this corpus size.
**Alternative considered:** Elasticsearch/Typesense — would demonstrate the JD's "search
infrastructure" good-to-have more directly, but risks the 10-minute Docker Compose bar and is
disproportionate for 300–500 rows.

---

### D005 — Topics: Large Language Models + Computer Vision
**Date:** 2026-08-16
**Decision:** Two topics for the corpus are "Large Language Models" and "Computer Vision."
Ingested via OpenAlex keyword search (`search=` param) rather than exact concept-ID filtering,
and tagged with our own `topics` table labels rather than mirroring OpenAlex's own taxonomy.
**Why:** Semantically distinct enough that the similarity feature produces visibly sensible
results (not two topics blurring together). Both are well-populated on OpenAlex, so hitting
300-500 papers with a recency filter is easy. Also directly useful reading material given the
candidate's own interest in AI engineering. Keyword search over concept-ID lookup keeps
ingestion simpler and is a legitimate "design the schema/approach yourself" choice per the
assignment brief, rather than just inheriting OpenAlex's structure.
**Alternative considered:** Generic "Natural Language Processing" (the assignment's own
example) — safer/more established as an OpenAlex concept, but less current and less directly
useful to the candidate than "Large Language Models" specifically.

### D006 — Schema validated against real Postgres+pgvector, not just code review
**Date:** 2026-08-16
**Decision:** Ran the Phase 1 migration (upgrade + downgrade + re-upgrade) against a real local
Postgres 16 + pgvector instance before committing, rather than trusting the autogenerated
migration blindly.
**Why:** Autogenerate produced one real bug (missing `import pgvector.sqlalchemy`, which would
have crashed `alembic upgrade` on a clean clone) — caught only by actually running it. Full-text
GIN index and ivfflat cosine index also had to be hand-added; autogenerate doesn't detect
functional/expression indexes.
**Alternative considered:** Trust autogenerate output as-is — rejected, too risky given the
assignment's "must run within 10 minutes of cloning" requirement.
